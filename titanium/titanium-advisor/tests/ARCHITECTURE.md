# Test Harness Architecture

How the multi-agent interview tests work, why they're designed this way, and what to watch out for.

## How the Two-Agent Test Works

```
Workflow loop (orchestrator):
  ┌─────────────────────────────────────────────────┐
  │                                                 │
  │  ┌─────────────┐    message    ┌─────────────┐ │
  │  │ Interviewer │ ──────────▶  │  Customer   │ │
  │  │   (Agent)   │ ◀──────────  │   (Agent)   │ │
  │  └─────────────┘    reply      └─────────────┘ │
  │       │                                         │
  │       │ MCP tool calls                          │
  │       ▼                                         │
  │  ┌─────────────┐                               │
  │  │  MCP Server │  ← stores all session state   │
  │  │ (server.py) │                               │
  │  └─────────────┘                               │
  │                                                 │
  └────────── repeats per section ──────────────────┘
                        │
                        ▼
              ┌─────────────────┐
              │ Reviewer Agent  │
              │ (YAML + reqs    │
              │  → pass/fail)   │
              └─────────────────┘
```

Each agent is **stateless** — spawned fresh every turn with no memory of prior turns. The MCP server is the source of truth for all session state (answers recorded, sections completed, current progress).

## Key Design Decisions

### 1. Minimal interviewer prompt — just enough context per turn

Each interviewer agent gets ONLY:
- **Session ID** — so it can call MCP tools
- **Current section name** — so it knows what to work on
- **Customer's last reply** — so it can map their answers to question IDs
- **Previous interviewer message** — so it knows what options were presented (needed when customer says "yes that looks right")

It does **NOT** get the full transcript history.

**Why:** The MCP server stores all session state. The agent calls `get_section_quick_mode` which tells it exactly what questions to ask and what nonce to use. Earlier versions passed the full growing transcript (~20-35k chars by section 8) which caused the 180s heartbeat timeout to trigger — the LLM couldn't start generating fast enough with that much context.

**The critical insight:** The MCP server is the memory. The agent is stateless. Each turn is a tiny, focused task: "record these answers, present the next section."

### 2. MCP server provides all guidance

The interviewer prompt is deliberately generic: *"You are an AI assistant helping a customer configure their AWS Landing Zone."* 

All interview logic — section ordering, question presentation, confirmation nonces, anti-bypass guards — comes from the MCP tool responses. The interviewer agent just follows what the tools tell it to do.

**Why:** This tests the real experience. When Q Developer or Kiro drives the interview, they get the same MCP responses. If the test passes, any LLM agent following the MCP guidance will produce correct results.

### 3. Tool restriction

The interviewer is told: *"You may ONLY use ToolSearch and mcp__titanium-advisor__* tools. Do NOT use Bash, Read, Write, or any other tools."*

**Why:** Without this restriction, agents that get confused (e.g. the MCP rejects a call) will fall back to Bash scripting — importing `server.py` directly, running Python one-liners, reading files to "understand" the problem. This bypasses the MCP protocol entirely and doesn't test the real agent experience.

### 4. Sonnet for the customer agent

The customer agent uses the `sonnet` model — cheaper and faster than Opus.

**Why:** The customer just generates a text reply based on the persona's requirements. No tool calls, no complex reasoning. Sonnet is more than capable and saves ~40% cost across a full run.

### 5. Session ID for parallel safety

When writing log files, the workflow finds its own transcript directory by grepping for the unique session_id:

```bash
WF_DIR=$(grep -rl "SESSION_ID" ~/.claude/projects/*/subagents/workflows/wf_*/agent-*.jsonl | head -1 | xargs dirname)
```

**Why:** An earlier approach used `ls -td wf_*/ | head -1` (most recently modified directory) which races when multiple workflows run in parallel. Each interview gets a unique session_id from the MCP server, making this grep deterministic regardless of timing.

### 6. Review file only — transcript via dump script

The workflow writes only a small review file (~8k chars) through an agent. The full transcript (~35k chars) is generated by `dump-workflow-log.py` from the raw agent files.

**Why:** Writing 35k+ chars through an agent means putting all that content in the agent's prompt. The LLM takes too long to start processing, triggering the 180s heartbeat timeout. The dump script reads raw files directly — instant, no LLM involved.

## Single-Agent (Fast) vs Two-Agent (Full)

| | Single-Agent (Fast) | Two-Agent (Full) |
|---|---|---|
| **Architecture** | One agent plays both sides — calls MCP tools AND decides answers based on persona requirements | Two separate agents alternate — interviewer calls MCP tools, customer responds naturally |
| **What it tests** | Config correctness (did the right values end up in the YAML?) | Conversational quality (does the MCP server guide an LLM well?) + config correctness |
| **Agents per run** | 3 (driver + reviewer + log writer) | ~25-30 (1 start + ~11 interviewer turns + ~11 customer turns + reviewer + log writer) |
| **Cost** | ~90k tokens, 5 min | ~450-530k tokens, 40-60 min |
| **Reliability** | Always completes (single agent, single MCP session) | Occasionally stalls on credential expiry or MCP server contention |
| **Finds UX bugs?** | No — agent self-directs, doesn't test how well the MCP guides a naive LLM | Yes — the interviewer only gets MCP responses as guidance, exactly like Q/Kiro would |
| **Persona fidelity** | Perfect — agent follows the script exactly because it has both the questions and answers | Approximate — customer agent sometimes deviates from persona (e.g. agrees to defaults it should decline) |
| **When to use** | After code changes to check nothing broke (regression) | Before releases to validate the end-to-end experience |

### Why both exist

The **fast test** catches **wiring bugs** — budget amount wrong, section missing, response not mapped to config. It's deterministic and cheap. Run it on every commit.

The **full test** catches **interaction bugs** — advisor bundles questions preventing individual opt-out, advisor over-recommends for beginner personas, advisor explains poorly, customer loses information between turns. These only surface in real two-party conversation. Run it before merging.

## What Causes Stalls (and how to avoid them)

| Cause | Symptom | Fix |
|-------|---------|-----|
| Agent prompt > ~20k chars | No first token within 180s | Keep prompts small — pass session_id not transcript |
| MCP server contention | Intermittent timeouts on tool calls | Avoid running many workflows against one stdio server |
| Expired credentials (SSO) | MCP calls hang indefinitely | Re-authenticate before running tests |
| Agent "catching up" on missed context | Falls back to Bash scripting | Use tool restriction + explicit state passing |
| Writing large content via an agent | Agent dies mid-file-write | Use dump script instead of agent for large outputs |

### The 180s Heartbeat Rule

The Claude Code workflow runtime kills an agent if it produces **no output** (no tool call, no text) for 180 seconds. This means:

- Keep prompts small so the LLM starts generating quickly
- If an MCP call takes >180s to respond, the agent dies
- 6 retries × 180s = 18 minutes wasted per stall
- The threshold is not configurable — design around it

## Cost Profile

| Scenario | Agents | Tokens | Time |
|----------|--------|--------|------|
| Fast test (any scenario) | 3 | ~90k | ~5 min |
| Full test (simple persona B) | ~23 | ~450k | ~7-40 min |
| Full test (complex persona A/C) | ~27-29 | ~530k | ~40-60 min |
| All 3 full tests in parallel | ~75-80 | ~1.5M | ~60 min |
